# DEF-019 — AMD-002 recorded a reason that never took effect

| Field | Value |
| --- | --- |
| Detected by | P02.GATE01 (review of the amendment log) |
| Severity | HIGH |
| Affected gate | PB.T06 (amendment mechanism) / P02.GATE01 |
| Status | CLOSED |

## What happened
A batch step was supposed to (1) declare `P02.REG01` and `P02.CONF02` in the
blueprint, (2) `sync` them into the ledger, then (3) record an amendment
explaining the implementation change.

Step 1 FAILED: the Python anchor `u("P02.CP01", M, "P02 checkpoint recorded", { depends_on: ["P02.GATE01"] }),`
no longer existed as a single line — prettier had reformatted it across three
lines — so the assertion raised. Despite `set -e`, the shell continued, `sync`
added 0 units, and **`AMD-002` was still written**, stating it authorized the
declaration of two new IDs.

Nothing was actually declared. `AMD-002` therefore records a reason that did
not happen, and its superseded/new hashes are identical (`eeea59ca` -> `eeea59ca`,
blueprint `f2e7328f` unchanged) — a vacuous amendment.

## Why HIGH
The amendment log is the audit chain that lets an implementation change
supersede GEN-000 without rewriting the trust root. An entry whose stated
reason never occurred corrupts exactly the record a future reader would rely on
to understand why the authorized hashes moved. A misleading provenance record is
worse than a missing one, because it reads as authoritative.

## Root cause
Two faults:
1. The edit matched a pre-prettier source shape. Anchors must be verified
   against the CURRENT file, not a remembered one.
2. The batch continued past a failed precondition, so a later step recorded a
   claim its predecessor had not established. Recording an amendment must be
   conditional on the change it describes actually having landed.

## Corrective action
- `AMD-002` is NOT deleted — the log is append-only and erasing it would repeat
  the original sin. It stands, with this defect as its explanation.
- `AMD-003` supersedes it with an accurate reason and the real hashes, recorded
  only AFTER the blueprint change and `sync` are verified to have landed.
- The blueprint edit is re-applied against the current file shape and its
  effect is asserted (`sync` must report the two new units) before any
  amendment is written.

## Retest
`sync` reports `P02.REG01` and `P02.CONF02` added; both units record PASS;
`ledger verify` exits 0. See `AMD-003-rationale.md`.
