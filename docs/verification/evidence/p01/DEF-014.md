# DEF-014 — an interrupted run had already emitted a certificate on stdout

| Field | Value |
| --- | --- |
| Detected by | P01.CLN01 |
| Severity | HIGH |
| Affected gate | P01.T07 / P01.CLN01 |
| Status | CLOSED |

## What happened
`P01.CLN01` proved teardown was complete (exit 130, worktree removed,
registration pruned, run dir removed, developer files untouched) — but the
transcript also recorded:

    stdout certificate emitted = YES

In `--hold` mode the CLI printed the full snapshot JSON to stdout and *then*
waited for a signal. A consumer capturing stdout would therefore hold a
syntactically valid snapshot certificate for a run that was subsequently
interrupted and torn down.

## Why this is HIGH
The frozen rule is explicit: an interrupted run "must exit non-zero and may
never report PASS". A non-zero exit is necessary but not sufficient — the
certificate itself is the artifact downstream phases consume. Emitting one for
a run whose materialized worktree no longer exists is precisely the class of
false-green this control plane exists to prevent, and it would have been
inherited by every later gate that reads snapshot.json from a pipeline.

## Root cause
The certificate was emitted as soon as it was BUILT rather than once the
lifecycle had COMPLETED. `--hold` (a test affordance for exercising signals)
therefore published a certificate for a run that by construction never
completes.

## Corrective action
Emission is now tied to lifecycle completion, not construction:
- `--hold` never writes the certificate to stdout; it reports only a stderr
  marker. The on-disk `snapshot.json` still exists for inspection and is
  removed by interrupt-time teardown.
- The stdout certificate is emitted only on the normal, non-held, successful
  path.

## Retest
CLN01 re-run: exit 130, teardown complete, all deltas zero, and
`stdout certificate emitted = NO`.
