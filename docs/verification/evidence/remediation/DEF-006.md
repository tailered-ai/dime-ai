# DEF-006 — DEF-002 validator mangled context names containing parentheses

| Field | Value |
| --- | --- |
| Detected by | DEF-002 corrective validation (first run) |
| Severity | LOW |
| Affected gate | DEF-002 corrective evidence only — no production or CI surface |
| Status | CLOSED |

## Origin
A NEW failure created by remediation, so it takes its own ID rather than being
folded into DEF-002 (frozen defect-loop rule).

## Root cause
The first validator derived the graduating set from the end-state block using
`line.split("(")[0]`. The context `Secret Scan (gitleaks)` legitimately contains
parentheses, so it was truncated to `Secret Scan`, which is not a live context
and therefore appeared to be "graduating". The validator reported
`MATCH graduating: false` / `OVERALL: MISMATCH`.

## Why this is a good failure
The documentation was correct; the checker was wrong, and it failed LOUDLY
rather than passing silently. A checker that cannot distinguish those two cases
is worthless, so the loud failure is the desired behaviour.

## Corrective action
Parse on the ANNOTATION COLUMN (`split(/\s{2,}/)`) instead of on `(`. The
end-state block separates a context from its annotation by 2+ spaces, so the
name is taken intact regardless of internal parentheses.

## Retest
Re-ran the corrected validator: `MATCH enforced: true`,
`MATCH graduating: true`, `end-state count: 14`, `9 + 5 == 14: true`,
`OVERALL: DOCUMENTATION AND LIVE EVIDENCE AGREE EXACTLY`, exit 0.
Evidence: `DEF-002-validation.txt`.
